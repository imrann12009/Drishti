# DRISHTI Architecture — Stage A

## Scope delivered

This repository contains the Stage B project foundation, Stage C accessible UI prototype, Android camera/2-D detection adapter, and configurable BLE/Wi-Fi transport adapters for DRISHTI. Real Raspberry Pi hardware, depth estimation, cloud processing, subscriptions, and OTA updates remain gated by external validation and release infrastructure.

## Product safety boundary

DRISHTI is an assistive navigation aid, not a safety-certification system. The app must never state that a road, crossing, stair, curb, or path is safe solely because of an AI or simulated result. Users must continue using their cane, guide dog, or established mobility techniques.

Every data source must be visible in the UI:

- **Demo / simulated:** generated by the local simulator; never presented as a live sensor result.
- **Device / live:** allowed only after a real device connection and validated protocol messages exist.
- **Unavailable / stale:** must be treated as unknown, not as safe.

## Architecture proposal

Use a feature-first layered architecture:

```text
lib/
├── app.dart                         # MaterialApp composition
├── main.dart                        # process entry point
├── core/
│   ├── theme/                       # accessibility-first visual tokens
│   ├── device/                      # protocol and BLE/Wi-Fi transport adapters (Stage F)
│   ├── speech/                      # TTS abstraction and message queue (Stage E)
│   ├── persistence/                 # persistent non-sensitive preferences
│   ├── entitlement/                 # Free/Pro entitlement boundary (Stage G)
│   └── updates/                     # app/remote/device update status (Stage H)
└── features/
    ├── onboarding/
    ├── home/
    ├── navigation/
    │   └── domain/                  # session state machine
    ├── settings/
    └── help/
```

Each feature should keep presentation, application/state, domain, and data concerns separate as it grows. Platform integrations are accessed through interfaces in `core/`; UI code must not call BLE, Wi-Fi, TTS, Firebase, or payment SDKs directly.

## Technology assumptions

| Area | Decision now | Reason / condition |
|---|---|---|
| UI | Flutter + Dart | Android-first and later portable to iOS if needed. |
| State | Small explicit state objects initially | Avoid adding a state-management package before the state/event surface is understood. Introduce Riverpod/Bloc only when multiple features need shared asynchronous state. |
| Persistence | Interface first; local implementation later | Preferences need a stable schema before choosing a storage package. |
| Device link | `DeviceConnectionService` interface later | BLE vs Wi-Fi depends on final Raspberry Pi/board, power budget, range, and pairing requirements. |
| Voice | `SpeechService` interface later | Bengali availability, offline behavior, and interruption rules must be verified on target Android devices. |
| Cloud | Optional Firebase adapters | Only after consent, retention, authentication, and failure behavior are defined. No Firebase dependency is needed for this prototype. |
| Hardware AI | Device-side Python is a future option | Depends on board thermal limits, accelerator availability, model latency, camera pipeline, and battery budget. |

No final BLE characteristics, Wi-Fi endpoints, sensor packet format, board model, or offline Bengali TTS engine is committed by this stage.

## State machine contract

The current `NavigationSession` model supports these states:

- `idle`
- `starting`
- `demoActive`
- `connecting`
- `navigating`
- `warning`
- `paused`
- `stopping`
- `error`

Invalid transitions throw `InvalidNavigationTransition`. The state machine is intentionally small and synchronous in Stage C. Device events, timeout handling, stale-data checks, and persistence belong in later stages.

## Future device protocol (provisional design only)

The future transport must carry an envelope shaped like:

```json
{
  "protocol_version": "0.1-provisional",
  "message_type": "obstacle_event",
  "timestamp": "2026-01-01T00:00:00Z",
  "session_id": "opaque-session-id",
  "payload": {},
  "error_code": null
}
```

This is a documentation shape, not an implemented or final wire format. Before Device Mode is enabled, the team must agree on authentication, replay protection, clock handling, schema validation, maximum message size, event ordering, timeout rules, and firmware rollback behavior.

## Major risks and mitigations

1. **False confidence in alerts** — label source and limitations; never translate unknown into safe.
2. **Sensor or connection failure** — surface stale/disconnected state; fail closed for safety-critical decisions.
3. **Speech overload** — priority queue, repetition suppression, and a separate critical-alert path.
4. **Accessibility regressions** — semantics, keyboard/focus review, contrast checks, large targets, and manual TalkBack testing on each release.
5. **Paid access bypass** — production entitlements must be verified by a trusted backend/store receipt, not a client-only flag.
6. **Remote update compromise** — signed artifacts, integrity validation, rollback, recovery, and power-loss strategy before any OTA implementation.
7. **Privacy leakage** — no continuous recording or cloud upload by default; consent and deletion behavior before analytics or scene processing.
8. **Hardware mismatch** — keep transport and sensor adapters behind interfaces until the board and protocol are selected.

## Roadmap

- **Stage A:** architecture, assumptions, risk register — documented here.
- **Stage B:** project structure, dependency baseline, setup instructions — delivered in this change.
- **Stage C:** accessible onboarding, dashboard, settings, help, and safety UI — delivered in this change.
- **Stage D:** navigation controller and simulator events kept behind a clearly labelled test/demo boundary; repeatable local event timeline, pause/resume, alert dismissal, and bounded in-session history are now implemented.
- **Stage E:** speech abstraction, prioritization, fallback, and verified device testing — speech boundary and queue are now implemented; platform TTS remains pending.
- **Stage F:** device service boundary, versioned protocol validation, stale-data handling, and transport adapter tests — the first production-boundary increment is now implemented. The real transport remains blocked on approved hardware and protocol details.
- **Stage G:** feature registry and mock Free/Pro entitlement boundary — registry/provider boundary is now implemented; trusted store/backend verification remains pending.
- **Stage H:** app/remote/device update status and release notes.
- **Stage I:** integration, accessibility, malformed-message, timeout, and error-path tests.
- **Stage J:** selected board/sensor integration plan, threat model, power and recovery validation.

Review gate: do not add production services, payment SDKs, OTA code, or real hardware assumptions until this foundation is reviewed.
